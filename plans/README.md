### The finding the audit missed

Plan 002's 256 KB test exposed a deadlock in `ProcessRunner`'s pipe drain: `FileHandle.bytes`
serialises reads across handles, so the `async let` drain was never concurrent. Any child
writing more than the 64 KB pipe buffer to stdout hung **forever**, taking `PortScanner`
and the whole UI with it. Reproduced standalone: 60 KB fine, 128 KB hangs, 256 KB fine when
stderr is not piped. Fixed by draining each pipe with a blocking read on its own thread
(4 MB in ~6 ms). Owner decided on 2026-08-28 to fix it inside 002 rather than defer it.

This directly contradicts two entries in "Findings considered and rejected" below — the
per-byte read and the "concurrent drain is fine" conclusion. Both were reached by reading
the code and measuring real `lsof` output (~1.2 KB), which never approaches the threshold
where the bug lives. **Left in place deliberately, as a record of how the audit got it
wrong**: only a test with a deliberately oversized payload found it.

## Findings considered and rejected

Recorded so nobody re-audits them:

- **`proc_name` truncation would break the kill re-validation in `ProcessKiller`.** Tested
  against a deliberately 44-character binary: both `lsof +c0` and `proc_name` return the same
  31-character string, because on macOS they read the same kernel field. The comment at
  `ProcessKiller.swift:87` is accurate. Not a bug.
- **`LsofRunner` sets `process.terminationHandler` from an unstructured `Task`, so a fast exit
  could be missed and the `await` would hang.** The ordering really is unguaranteed, but
  Foundation on macOS fires a handler registered after the process has already exited
  (verified directly). Worth a comment one day; not a live defect.
- **Reading the pipe one byte at a time is a performance problem.** Measured: real `lsof`
  output on a developer machine is 1,252 bytes and the command takes ~36 ms. Roughly 1,200
  loop iterations every two seconds is nothing. Plan 002 adds a 256 KB test so a future
  chunked read has something to prove itself against, but there is no problem to fix today.
- **Security review found nothing.** Absolute executable path, fixed arguments, empty
  environment, no shell anywhere, PID re-validated against the process name before every
  signal, hardened runtime on, entitlements file empty, sandbox off by documented necessity,
  zero network calls, no secrets in the repo, `.gitignore` covers signing material and DMGs.

## Findings deliberately left unplanned

- **No logging anywhere.** `PROJECT_SPEC.md:258` specifies `os.Logger` with subsystem
  `app.squatter`; there is not a single `Logger` in the source. It means a user reporting "it
  shows nothing" leaves no diagnostic trail. Low impact for a tool whose failure modes are all
  visible in the UI, and adding logging to an app that deliberately touches no network is a
  small, uncontroversial change the owner can make whenever it starts to hurt. Skipped to keep
  this batch to work that pays for itself.
- **`String(localized:)` everywhere, but no String Catalog.** The whole UI is wrapped for
  localization and none of it is actually translatable — there is no `.xcstrings` and
  `developmentLanguage` is `en`. Either add the catalog or drop the wrappers; both are product
  decisions, not defects.

## Direction (options for the owner, not defects)

Raised during the audit and left for the owner to weigh:

- **Automate the release.** Two M3 tasks remain and the whole pipeline runs off one machine
  with a local `squatter` keychain profile. A tag-triggered workflow (archive → notarize →
  upload DMG → bump the cask sha256) is the difference between shipping v0.1.1 and not
  bothering. Plan 004 is the first step and says so in its maintenance notes.
- **Docker awareness (P2 in the spec).** Docker-published ports surface as
  `com.docker.backend`, which tells the user nothing and must not be killed. Annotating the
  container and offering "Stop Container" is the one feature that would make Squatter better
  than `lsof -i` rather than merely faster. It costs a second subprocess, which is a
  deliberate exception to golden rule #7 — a decision, not a detail.
- **Native `proc_pidfdinfo` instead of the `lsof` subprocess (P2).** Removes the external
  binary, the process spawn, and everything plan 003 defends against. Roughly 150 lines of
  `libproc`, and `LsofParser`'s fixture tests would be replaced by a different seam. Worth it
  only if the goal is an app with no external moving parts.
